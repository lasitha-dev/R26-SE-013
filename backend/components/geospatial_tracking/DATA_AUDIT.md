## 2. CSV source (`Latest Reported Events (3).csv`)

- 2407 rows, single disease (`Lumpy skin disease`), all rows
  `Diagnosis Status = Confirmed`.
- 37 distinct countries. Thailand (817), Malaysia (323), Russian Federation
  (189), Tunisia (187), Republic of Korea (133) dominate. **Sri Lanka: 12
  rows.**
- Columns: `Event ID, Disease, Serotype, latitude, longitude, Locality,
  Country, Region, observation date, report date, Species, Diagnosis
  Source, Humans Affected, Human Deaths, Diagnosis Status`.
- `Serotype`, `Humans Affected`, `Human Deaths` are **100% empty** — not
  usable fields for this dataset.
- `latitude`/`longitude`: 0% missing.
- `observation date`: 4.7% missing (112/2407); `report date`: 0% missing.
- No duplicate `Event ID` values within the file — but see §4, internal
  near-duplication is real at the row-content level, not the ID level.
- `Region` is a **continent** grouping (`Europe`, `Asia`, `Africa`, ...),
  not an administrative subdivision. It must never be mapped to `admin1`.
- `Event ID` values use the `UNFAO-LEG-######` / `UNFAO-HQ-#####` namespace
  (FAO EMPRES-i). This is a **different ID space** from WAHIS's numeric
  Event IDs (e.g. `3473`) and `OB_######` outbreak IDs used in the PDF
  reports — the two sources cannot be joined by ID and must be matched by
  country + location + date + species (Phase C).

## 3. WAHIS PDF sources

All four PDFs are genuine WAHIS "Event" reports (Immediate Notification or
Follow-up Report), one event ID each, containing a nested list of outbreak
blocks. `pypdf` text extraction was used (no OCR/rendering tool was
available in this environment — `poppler-utils` is not installed).

| File | Event ID | Country | Outbreak blocks | Approx-location flagged |
|---|---|---|---|---|
| Event_3473.pdf | 3473 | Sri Lanka | 6 | 0 |
| Event_5822.pdf | 5822 | Thailand | 2 | 0 |
| Event_5868.pdf | 5868 | Thailand | 4 | 3 |
| Event_3644.pdf | 3644 | Thailand | **670** | 197 |

Event_3644.pdf is a national-scale Thailand LSD event spanning 2021-03-10 to
2024-01-09, with 670 individually dated, geolocated outbreak blocks — by far
the largest single source. It was processed incrementally (page 1 for event
metadata, structural sampling, then a full programmatic pass) rather than
dumped into conversation.

**Parser coverage on Event_3644.pdf (670 outbreak blocks):** outbreak_id
670/670, species 670/670, outbreak dates 670/670, coordinates 667/670
(99.6%). Sanity checks passed: all outbreak dates fall within the event's
own start/end range, all coordinates fall within a plausible
Thailand bounding box, no negative quantitative values, no duplicate
outbreak IDs.

**Known parser limitation (3/670 records, 0.4%):** a small number of
outbreak blocks have their LOCATION table row's column order visibly
reshuffled by a mid-row PDF page break (locality name emitted *after* the
coordinates instead of before, with the "(Approximate location)" flag
emitted after "- Animal" instead of before it). The parser correctly leaves
`latitude`/`longitude` as `None` for these rather than guessing a field
mapping that could silently be wrong. Fixing this needs a layout-aware PDF
extractor (e.g. `pdfplumber` table extraction) — deferred to Phase B.

**Known parser limitation (all outbreak blocks):** `admin1`/`admin2`/`admin3`
are **not** populated. The WAHIS "FIRST/SECOND/THIRD ADMINISTRATIVE
DIVISION" line flattens to space-separated text with no delimiter, and
division names are themselves multi-word (e.g. "Chiang Mai", "Tha Wang
Pha"), so naive whitespace splitting would silently fabricate incorrect
boundaries. The raw line is preserved verbatim in
`extra["admin_line_raw"]`; proper segmentation needs either a layout-aware
extractor or a gazetteer-assisted parser (Phase B).

## 4. Cross-source overlap (critical for Phase C dedup)

The CSV's 12 Sri Lanka rows and Event_3473.pdf's 6 outbreaks describe the
**same underlying events**:

- Each of the 6 real outbreaks (Kopay, Chavakachcheri, Nallur, Murunkan,
  Manthei west, Vavuniya — all Sept–Oct 2020) appears **twice** in the CSV
  under two different `Event ID` values with slightly different coordinate
  decimal precision (e.g. `9.062135` vs `9.0621351`), and again as one
  record each in the PDF under WAHIS `OB_#####` IDs. Coordinates and dates
  match closely enough to be confidently the same 6 real-world outbreaks
  reported three times across two source files.
- This pattern generalizes: 351/2407 CSV rows (14.6%) fall into 160 groups
  that share `(country, locality, onset_date)` but have distinct `Event
  ID`s — i.e. the CSV itself is not internally deduplicated, independent of
  any PDF overlap.
- **Implication for Phase C:** naive concatenation of CSV + PDF records
  would substantially overcount outbreaks. Deduplication cannot rely on ID
  matching (the ID namespaces don't overlap) and must use explainable
  matching on country + location + date (+ coordinate proximity) + species,
  exactly as the master prompt's Phase C specifies.

## 5. GPS quality

- CSV source: no explicit precision/approximation marker on any row. All
  CSV-derived records get `gps_quality = UNKNOWN` (never `EXACT`) — the
  varying decimal precision seen between duplicate rows is not a reliable
  proxy for accuracy and is not used as one.
- PDF source: WAHIS explicitly marks some coordinates
  `(Approximate location)`. Where present, `gps_quality = APPROXIMATE`;
  otherwise `EXACT`. 200 of 682 total PDF outbreak blocks (197 in
  Event_3644 + 3 in Event_5868) are explicitly approximate.
- Confirmed case of shared approximate coordinates across **distinct**
  outbreak IDs (Event_5868: `OB_139551`/`OB_139549`/`OB_139550` all report
  `18.689547, 98.994437 (Approximate location)` for different villages).
  The parser keeps these as separate records — per the master prompt's GPS
  rule, shared approximate coordinates must never be silently collapsed
  into one outbreak.

## 6. Date semantics

**Correction (post-Checkpoint-1):** Checkpoint 1 originally set every
record's availability to `report_date` / `REPORT_PROXY`. On review this
conflated three chronologies that must stay separate:

- **(A) biological/event chronology** — `outbreak_start_date`,
  `outbreak_end_date`, `event_start_date`, `event_end_date`, `onset_date`.
- **(B) source-document chronology** — `confirmation_date`, `report_date`,
  `notification_date`.
- **(C) model operational availability** — when a real-time surveillance
  system would actually have known about the outbreak. Neither raw source
  records this, so it is a *distinct* field
  (`operational_availability_date` / `operational_availability_quality`),
  always `None` / `UNKNOWN` for every raw record produced today — never
  silently inferred from (A) or (B).

The specific failure mode this corrects: WAHIS `report_date` is a single
event-level filing date shared across every outbreak block in a report.
Treating it as availability made a 2020/2021 outbreak look like it only
became "available" on its follow-up report's (possibly much later) filing
date — e.g. Event_3473 (`confirmation_date = 2020/12/18`, `report_date =
2023/07/28`, nearly 3 years later) or Event_3644 (one `report_date =
2024/01/09` final follow-up report bundling 670 outbreak blocks whose own
`outbreak_start_date`s span 2021-03-10 to 2024-01-09). A 2021 outbreak
contained in a 2024 final follow-up report must not automatically become a
"2024 outbreak" for epidemiological chronology.

Two concrete examples showing why `report_date` cannot be treated as
`confirmation_date` or `event_end_date` either:

- Event_5868: `event_end_date = 2024/04/21`, but `report_date =
  2024/09/18` — a ~5-month gap between the disease event ending and this
  report being filed.
- Event_3473: `confirmation_date = 2020/12/18`, `report_date =
  2023/07/28` — nearly 3 years later (this is "Follow-up report 1" for a
  2020 event).

`RawOutbreakRecord` now carries two independent availability field pairs
(schema detail in §7):

- `operational_availability_date` / `operational_availability_quality` —
  the only fields a future **STRICT_OPERATIONAL** validation mode may use.
  `ACTUAL` requires real "system knew by" evidence (enforced in
  `__post_init__`); with none, it stays `None` / `UNKNOWN` and the record
  simply cannot participate as "known by date X" in that mode. Never
  backfilled from `report_date`.
- `proxy_availability_date` / `proxy_availability_quality` — a
  **RETROSPECTIVE_PROXY**-mode-only, research-sensitivity-analysis
  substitute, explicitly labeled `EVENT_DATE_PROXY` (WAHIS: the outbreak
  block's own `outbreak_start_date`) or `OBSERVATION_DATE_PROXY` (CSV: the
  row's `observation date`). `__post_init__` raises if this is ever set to
  `ACTUAL` — a proxy can never be presented as real-time availability, no
  matter how much evidence backs the underlying date.

Both `_date`/`_quality` pairs leave `event_start_date`, `outbreak_start_date`,
`confirmation_date`, `report_date`, and `onset_date` untouched — none of
those original fields are ever overwritten by a derived proxy.

## 13. Parser gap fix — Event_3644.pdf missing coordinates

Checkpoint 1 flagged 3/670 outbreak blocks in Event_3644.pdf with
unresolved coordinates due to a PDF page-break artifact. Investigated
directly against the source PDF text (never guessed):

- **OB_92005, OB_91966**: not actually reshuffled — their locality names
  contain parentheses and wrap across a line break (e.g. "Si Racha
  (Protected Area Regional \nOffice 2 Sriracha)"), which the original
  locality regex's character class rejected. Fixed by widening the
  character class to accept `()` and newlines, **scoped to the LOCATION
  table's own section** of the outbreak block (not the whole block) to
  avoid the widened class capturing earlier section headers — a
  regression the existing Checkpoint 1 test suite caught immediately
  during development.
- **OB_100298**: genuinely reshuffled column order — coordinates before
  locality, with the approximate-location flag emitted after "- Animal"
  instead of before it. A second, narrow fallback pattern recovers this
  exact literal order, tried only when the normal-order pattern finds
  nothing.

**Result: 0/670 missing coordinates in Event_3644.pdf (previously 3/670);
0/682 across all four WAHIS PDFs.** Full detail in `DATA_PROVENANCE.md`
§5. 6 new regression tests added
(`test_reshuffled_coords_before_locality_recovers_coordinates`,
`test_locality_with_parentheses_and_linewrap_is_parsed`,
`test_reshuffled_or_parenthesized_location_never_captures_earlier_headers`,
and matching `dedup`/`normalize` coverage).

admin1/admin2/admin3 segmentation remains unresolved and provisional
(unchanged from Checkpoint 1) — the raw division-hierarchy line is
preserved verbatim in `extra["admin_line_raw"]`; still needs a
layout-aware extractor or gazetteer (deferred to Phase B).

## 19. Scientific decision gate

Assessed **separately**, per the Checkpoint 2 requirement — not one
blanket rating:

- **A. Risk-surface development: LIMITED.** 2179 geolocated points across
  37 countries is a reasonable substrate for a coarse, exploratory
  surface, but 1520/2179 (70%) carry `UNKNOWN` GPS precision (CSV never
  states it), admin1/2/3 is still unpopulated for WAHIS records (§13), and
  159 LOW-confidence duplicate clusters (mostly Thailand) risk locally
  inflating point density if not excluded first. Usable for coarse/
  regional exploration; not yet defensible for fine-resolution work
  without a precision/independence filter pass.
- **B. Direction evaluation: LIMITED.** Retrospective proxy dates exist
  (`proxy_availability_date` + `proxy_availability_source_field`, fully
  auditable), but `operational_availability_date` is `UNKNOWN` for 100% of
  records — any direction analysis is necessarily RETROSPECTIVE_PROXY-mode
  only, never a real-time-availability reconstruction. Combine with the
  `spatial_independence` flag (not yet used as a modeling filter, only
  computed) before any directional vector is derived from two points that
  might share a snapped coordinate.
- **C. Spread-front-rate estimation: LIMITED.** Event_3644.pdf (670
  outbreaks, near-daily cadence, 2021-03 to 2024-01) is a genuinely

# Checkpoint 3.5 — Date Purity, Animal-Count Uncertainty, Domain Safety Correction

Added 2026-08-18. A correction checkpoint only — no new architecture, no
historical episode construction, no GIS/ST-DBSCAN/model/FastAPI/frontend
work. Full technical detail in `REPOSITORY_DESIGN.md` §12.

## 33. Bug found and fixed

Checkpoint 3's `services/aggregation.py` used one generic "best report
date" helper (trying `onset_date`, then `submitted_at`,
`notification_date`, `confirmation_date`, `accepted_at` in turn) for two
different jobs at once: deciding which reports cluster into an episode,
**and** becoming `OutbreakEpisode.onset_date`. That let an operational
workflow timestamp silently masquerade as a biological onset date
whenever a report had no real `onset_date` — a real scientific-integrity
bug that Checkpoint 3's own test suite did not catch, because every test
that asserted on `onset_date` happened to also supply a real one on every
report.

Also found: Checkpoint 3's `affected_animals` rule ("distinct animal_id
count, plus one per unidentified report") could overstate the true count,
since two unidentified reports might describe the same physical animal
and there was no way to tell them apart.

## 34. Corrected date model — four separated concepts

1. **Biological onset** (`OutbreakEpisode.onset_date`) — real
   `AnimalReport.onset_date` values only, `None` otherwise.
2. **Episode grouping date** (`episode_grouping_date` /
   `episode_grouping_date_quality`) — used only to decide clustering;
   labeled `BIOLOGICAL_DATE` or `OPERATIONAL_PROXY`
   (`domain.enums.GroupingDateQuality`) so a caller always knows which
   kind of evidence it is; `UNKNOWN`/`None` when neither exists.
3. **Operational availability** — unchanged in spirit, tightened to an
   explicit two-step hierarchy: earliest `accepted_at` of
   ACCEPTED/CONFIRMED reports first; earliest `confirmation_date` of
   CONFIRMED reports only as a fallback if no `accepted_at` exists
   anywhere; otherwise `None`/`UNKNOWN`. Never `onset_date`,
   `submitted_at` alone, or `created_at`.
4. Reports with no reliable grouping date at the same `(farm_id,
   disease)` are attached to a dated cluster only via a shared known
   `animal_id` (strong identity evidence); anything left over is grouped
   only by shared `animal_id` among itself or stands alone, and every
   episode assembled this way sets `aggregation_review_required = True`.

## 35. Corrected affected-animal semantics

`affected_animals` (now nullable) / `affected_animals_quality`
(`domain.enums.AnimalCountQuality`) / `unidentified_report_count`:

- **CASE A** all reports identified: `affected_animals` = distinct
  `animal_id` count, quality `EXACT`.
- **CASE B** mixed: `affected_animals` = distinct KNOWN `animal_id` count
  (a genuine lower bound), quality `LOWER_BOUND`,
  `unidentified_report_count` = the rest.
- **CASE C** none identified: `affected_animals = None`, quality
  `UNKNOWN`, `unidentified_report_count` = all of them.

A `LOWER_BOUND`/`UNKNOWN` count must never be treated as exact
source-pressure for later modeling without an explicitly developed rule —
documented in both `REPOSITORY_DESIGN.md` and the field's own docstring.

Duplicate `report_id` safety: `aggregate_reports_into_episodes` now
dedupes its input by `report_id` before any grouping/counting
(`_dedupe_by_report_id`), on top of the repository's pre-existing `INSERT
OR REPLACE` upsert semantics — a re-submitted report can never inflate a
count or contribute twice to an episode, at either layer.

## 36. SQLite changes

`outbreak_episodes` gained 6 columns: `affected_animals` (now nullable),
`affected_animals_quality`, `unidentified_report_count`,
`episode_grouping_date`, `episode_grouping_date_quality`,
`aggregation_review_required`. No other table changed.
`historical_outbreak_records` — **untouched**. The gitignored,
development-only dev DB file was deleted and recreated (schema can't be
`ALTER`ed by `CREATE TABLE IF NOT EXISTS`); the historical corpus was
re-imported unchanged (2587 rows, same as Checkpoint 3). No raw source

### Wind-vector correction

Checkpoint 5's `u10`/`v10` paired `wind_speed_10m_max` (a daily maximum)
with `wind_direction_10m_dominant` (a daily mode) — two independent
summary statistics that do not describe one coherent wind vector. This
code path is **removed** from `fetch_daily_weather` (not supplemented).
The new primary path, `build_pre_t0_weather_summary`, retrieves PAIRED
HOURLY `wind_speed_10m`/`wind_direction_10m`, converts each hour's own
pair to `(u, v)` independently, and averages the COMPONENTS — never
averaging compass bearings arithmetically.

### t0 temporal-purity correction

`T0Precision.DATE_ONLY` (this corpus's normal case) now enforces
`weather_timestamp < t0_start` (midnight UTC of the t0 calendar date,
strict) — a full t0-day of weather is never assumed available, since the
exact intra-day outbreak-trigger moment is unknown. `TIMESTAMP` mode
relaxes to `<=` for a genuine exact instant. `build_pre_t0_weather_summary`
never requests or considers a post-cutoff hour at all, so it cannot leak
`REALIZED_FUTURE_REANALYSIS` even in principle.

### Land-cover year correction

Event_3473 (Sri Lanka) is a real 2020 event; Checkpoint 5's smoke test
used WorldCover 2021 v200 with an inaccurate "nearest available year"
comment. Corrected to WorldCover 2020 v100 —
`resolve_landcover_temporal_role("2020", target_year="2020")` now
correctly reports `YEAR_MATCHED_REFERENCE`. Event_3644 (Thailand, 2021)
was already using the matching 2021 v200 product; now additionally
labeled `YEAR_MATCHED_REFERENCE` explicitly rather than left implicit.
The land-cover fraction statistic itself is renamed "pixel-count zonal
fraction" (it was always `count(class)/count(valid)` on the native
EPSG:4326 grid, never true metric area-weighting) — the Checkpoint 5
docs overstated this as "area-weighted"; the underlying numbers are
unchanged, only the terminology and the WorldCover product year used
for Sri Lanka changed.

### 1. Weather valid-time vs. availability-time — official evidence

Confirmed 2026-08-19 against ECMWF/Copernicus's own documentation
(https://confluence.ecmwf.int/spaces/CKB/pages/76414402/ERA5+data+documentation):
"daily updates for ERA5T are available about 5 days behind real time";
"the final ERA5 data are available about two months after the month in
question." Checkpoint 5.5's `OBSERVED_REANALYSIS_AT_T0` role name and
its documentation ("information a real deployed forecaster would have
had") conflated a value's meteorological valid_time with its real-world
publication time — these ARE different questions for a retrospective
reanalysis. Corrected:

- `WeatherTemporalRole.OBSERVED_REANALYSIS_AT_T0` → renamed
  `RETROSPECTIVE_REANALYSIS_STATE_PROXY` (answers only: was this
  value's valid_time pre-t0?).
- New `WeatherAvailabilityQuality` enum (`ACTUAL`/`LAG_RULE_PROXY`/`UNKNOWN`)
  — `UNKNOWN` by default in the primary path; `LAG_RULE_PROXY` only
  under the optional, explicit `strict_operational_availability=True`
  sensitivity mode; `ACTUAL` never produced anywhere in this pipeline
  (no exact historical ERA5/ERA5T publication timestamp is known).
- Real consequence, not hypothetical: enabling
  `strict_operational_availability=True` with the smoke test's
  `lookback_hours=24` eliminates every sample for the Sri Lanka AOI (0
  of 24 hours satisfy `valid_time + 5 days <= t0` — the entire 24h
  lookback sits inside the 5-day lag). Reported honestly as `MISSING`
  for all 8 affected feature names, not fabricated.

### 2. Timezone resolution — method and real evidence of necessity

`services/geospatial/weather/t0_resolution.py`, using `timezonefinder`
(new dependency, `requirements.txt`, offline polygon lookup,
`timezone_at_land` — not `timezone_at`, which falls back to
conventional "Etc/GMT+N" zones for ocean/poles and would make "cannot
be resolved" untestable) + Python's `zoneinfo`.

**Empirically demonstrated why a hardcoded/convenience-API offset is
unsafe**: Open-Meteo's own `timezone=auto` parameter, queried for
2000-06-01 at the Sri Lanka smoke coordinate, returns
`utc_offset_seconds=19800` (today's +5:30) — the SAME value it returns
for a 2020 query. `zoneinfo.ZoneInfo("Asia/Colombo")` for the same two
dates returns +6:00 (2000) vs. +5:30 (2020) — genuinely different,
because Sri Lanka's real UTC offset changed historically. Open-Meteo's
convenience field is NOT historically offset-accurate; `zoneinfo` is.
This is why timezone NAME resolution (offline, `timezonefinder`) and
historical OFFSET computation (`zoneinfo` + the actual historical date)
are kept as two separate steps.

**Resolved timezones for both smoke AOIs** (offline, deterministic):
Sri Lanka Chavakachcheri → `Asia/Colombo`; Thailand Muang Suang →
`Asia/Bangkok`. Both match Open-Meteo's own live-queried `timezone=auto`
name exactly (name resolution agrees; only historical offset computation
differs, as expected).

## 73. Checkpoint 6C.5 — cell-vs-source factor index correction, complete grid contract, hazard input identity, numerical relative-risk safety

**The bug**: Checkpoint 6C's `HazardFactors` grouped `host_factor`/
`environmental_suitability_factor`/`water_context_factor` under a
single per-SOURCE bag. These are actually CELL properties — every
source contributing to a cell must read the identical value, or the
model could let two sources silently disagree about the same cell's
own environment. Caught and fixed before any real feature->factor
transformer was built, so no real provenance was ever affected.

**The fix** (full design: `HAZARD_ENGINE_PROTOCOL.md` §0, §17-19):
`CellHazardFactors(grid_cell_id, host_factor,
environmental_suitability_factor, water_context_factor)` — one object
per cell. `SourceHazardFactors(source_id, source_strength_factor)` —
one object per source (the only genuinely source-indexed factor,
still never derived from `affected_animals`/DQS/cluster role/GPS
quality/case count). Legacy combined `HazardFactors` kept only as
`LEGACY_6C_FIXTURE_ONLY`; `compute_source_hazard` structurally no
longer accepts a combined `factors=` parameter at all (verified,
`test_index_07_primary_api_does_not_accept_combined_source_indexed_factors`).
`compute_source_hazard` cross-checks `geometry.grid_cell_id ==
cell_factors.grid_cell_id` and `geometry.source_id ==
source_factors.source_id` itself — dictionary placement is never
trusted alone.

**New `meteorology.py`**: `CellMeteorology(grid_cell_id, wind_vector,
wind_speed_factor)` makes wind explicitly cell-indexed;
`expand_uniform_meteorology` is the only sanctioned way to turn one
shared fixture vector into a `wind_by_cell` mapping — the repetition
across cells is explicit, never implicit.

**Complete grid contract** (`snapshot.build_hazard_snapshot`): now
iterates an explicit `expected_grid_cell_ids`, never merely
`geometry_by_cell.keys()` — a cell entirely missing from
`geometry_by_cell`/`cell_factors_by_cell` still produces exactly one
`CellHazardResult` (`CELL_HAZARD_INCOMPLETE`, explicit missing
requirement), never silently vanishing. Missing source geometry,
missing source factors, and missing cell factors all resolve to an
explicit incomplete status with a named requirement — never an
uncontrolled `KeyError`, never a silently-dropped source. Duplicate
`active_source_ids` and any source appearing in
`geometry_by_cell`/`source_factors_by_source` without being in
`active_source_ids` both raise `ValueError` immediately, before any
hazard math runs.

**`hazard_input_signature_hash`** (new): a deterministic SHA-256 of
every effective mathematical input — expected grid-cell set, cell
factors, source factors, geometry, per-cell meteorology, active source
IDs — immune to dict insertion order, never including `generated_at`.
`hazard_snapshot_id` now also covers this hash plus the expected
grid-cell set, so changing ANY effective input (a cell factor, a
source strength, a wind vector, an added/removed grid cell) changes
the snapshot's own identity, while `generated_at` never does.

**Numerically safe relative-risk link**: `compute_relative_risk_index`
now returns `RelativeRiskResult(value, status)` using
`-math.expm1(-H)` (avoids small-`H` cancellation); for `H` large enough
that float64 cannot represent the true sub-`1.0` result
(`status=NUMERIC_SATURATION_ADJUSTED`, `value` nudged to
`math.nextafter(1.0, 0.0)`), never an unlabeled exact `1.0`. `H=0`
still returns exactly `0.0` (no epsilon floor).

## 76. Checkpoint 6D.6 — effective weighted raster identity, value-conflict firewall, full-stratum compatibility, honest readiness (corrects §75)

**The gap in §75's `sample_identity`**: it identified only the SET of

density values — collapsing them to one reference observation was

**The fix**: new `contributing_pixel_sample_support` in `fao_glw.py`

fixtures (`WEIGHTED-REF-01..07`) and the live GLW4 cache: two cells

digests; two cells sharing the same effective weighted blend correctly

duplicate**: `reference_profile.py`'s pooling loop now detects a
